# بررسی و نقشه بومی‌سازی سراسری سفر سرویس

تاریخ بررسی: 2026-10-24  
مبنای بررسی: فایل‌ها و فهرست‌های قابل مشاهده در شاخه `main` مخزن GitHub. این سند گزارش بررسی ایستا است؛ به‌معنای اجرای تست، ممیزی کامل همه فایل‌ها یا اثبات آمادگی تولید نیست.

## نتیجه اولیه

- رابط وب فعال پروژه در `client-web` و مبتنی بر Next.js 16، React 19 و TypeScript است.
- نقطه ورود سراسری رابط در `client-web/src/app/layout.tsx` و سبک‌های عمومی در `client-web/src/app/globals.css` قرار دارد.
- مسیرهای اصلی کد در `client-web/src/app`، `src/components`، `src/context`، `src/lib`، `src/modules` و `src/services` هستند.
- یک صفحه مستقل ورود در `00-frontend/login.html` نیز وجود دارد؛ باید مشخص شود این صفحه هنوز در مسیر واقعی اجرا استفاده می‌شود یا صرفاً فایل قدیمی/کمکی است.
- در فهرست اولیه `src/lib` فقط `auth.ts` و `phone.ts` دیده شد؛ زیرساخت مشترک ترجمه در این پوشه آشکار نبود. این مشاهده محدود به مسیرهای بررسی‌شده است و به‌تنهایی اثبات نمی‌کند که هیچ قابلیت ترجمه‌ای در هیچ جای مخزن وجود ندارد.
- اسکریپت‌های رابط وب شامل `npm run lint` و `npm run build` هستند. تست خودکار مستقل برای بومی‌سازی در اسکریپت‌های مشاهده‌شده تعریف نشده است.

## اصل مهم: بومی‌سازی فقط ترجمه متن نیست

بومی‌سازی باید زبان، جهت نوشتار، قالب اعداد و تاریخ، واحد پول، منطقه، منطقه زمانی، تلفن، دسترس‌پذیری، فراداده موتور جست‌وجو و قالب‌های پیام/رسید را پوشش دهد؛ بدون آنکه تغییر زبان، داده مالی یا منطق امنیتی را تغییر دهد.

## تصمیم‌های معماری

### زبان و منطقه

- شناسه‌های زبان/منطقه بر پایه BCP 47 باشند؛ برای شروع `fa-AF`، `fa-IR`، `ps-AF`، `ar`، `en` و `ur`.
- زبان، کشور، واحد پول و منطقه زمانی چهار مفهوم مستقل باشند؛ انتخاب زبان نباید به‌طور خودکار کشور یا پول حساب را عوض کند.
- فارسی/دری، پشتو، عربی و اردو راست‌به‌چپ؛ انگلیسی چپ‌به‌راست.
- زبان انتخاب‌شده کاربر بر تشخیص مرورگر اولویت داشته باشد. تشخیص مرورگر فقط مقدار پیش‌فرض اولیه باشد.
- کلیدهای ترجمه پایدار و معنایی باشند، مانند `booking.status.confirmed`. در نبود ترجمه، متن جایگزین قابل‌فهم نمایش داده شود؛ هرگز کلید خام به کاربر نشان داده نشود.

### نمایش و قالب‌بندی

- برای تاریخ و عدد از `Intl.DateTimeFormat` و `Intl.NumberFormat` استفاده شود؛ قالب داده ذخیره‌شده از قالب نمایش جدا بماند.
- برای چیدمان CSS از ویژگی‌های منطقی مانند `margin-inline`، `padding-inline`، `inset-inline` و `text-align: start` استفاده شود؛ اصلاح صرفاً با وارونه‌کردن کل صفحه کافی نیست.
- شماره تلفن باید با کد کشور صریح و قواعد اعتبارسنجی/نرمال‌سازی معتبر مدیریت شود؛ کشور از زبان حدس زده نشود.
- مبالغ با کد پول استاندارد ISO 4217 و دقت مناسب ذخیره شوند. تغییر زبان یا قالب نمایش نباید مبلغ تراکنش یا نرخ تبدیل را تغییر دهد.
- تاریخ‌های محلی، از جمله تقویم هجری شمسی یا هجری قمری، فقط در لایه نمایش و با انتخاب/قاعده روشن اعمال شوند؛ زمان ذخیره‌سازی و منطقه زمانی باید صریح و قابل‌آزمایش باشد.

### امنیت و حاکمیت

- ترجمه یا پنهان‌کردن دکمه جایگزین مجوزدهی سمت سرور نیست.
- دسترسی، قیمت، وضعیت رزرو، پرداخت و کیف پول مستقل از زبان بمانند.
- متن‌های کاربر، داده سفر و نام شهرها نباید به‌عنوان کلید ترجمه یا منطق برنامه استفاده شوند.
- پشتیبانی از کشور یا روش پرداخت تنها پس از بررسی واقعی ارائه‌دهنده، قوانین، مالیات و محدودیت‌های همان کشور فعال شود.

## مراحل پیشنهادی اجرا

1. **تکمیل ممیزی:** بررسی `layout.tsx`، `globals.css`، صفحات واقعی، کامپوننت‌ها، فرم‌ها، مسیرهای احراز هویت و هر متن ثابت؛ تعیین صفحه ورود قدیمی/فعال و تهیه فهرست نقاط hard-coded.
2. **زیرساخت کم‌خطر:** ایجاد رجیستری locale، توابع جهت نوشتار، قالب‌بندی عدد/تاریخ/پول، fallback ترجمه و تست واحد مستقل؛ بدون بازنویسی یک‌باره همه صفحات.
3. **اتصال پوسته:** تنظیم `lang` و `dir` در نقطه ورود، ذخیره انتخاب کاربر با روش سازگار با معماری پروژه، و اصلاح CSS عمومی با ویژگی‌های منطقی.
4. **جریان‌های حیاتی:** ورود/ثبت‌نام، سفر و جست‌وجو، رزرو، وضعیت‌ها، راننده، باربری، پرداخت و رسید.
5. **پنل‌ها و ارتباطات:** پنل مدیر، پشتیبانی، فروشنده و تور؛ پیامک، ایمیل، اعلان، PDF/QR و خطاهای اعتبارسنجی.
6. **منطقه‌ای‌سازی:** کشور، پول، منطقه زمانی، تقویم، واحدها و قالب تلفن با داده‌های مستقل و آزمون‌های مشخص.
7. **آمادگی انتشار:** تست lint و build، تست‌های واحد، بررسی بصری RTL/LTR، دسترس‌پذیری، SEO و PWA؛ بازبینی انسانی ترجمه‌ها پیش از انتشار.

## معیارهای پذیرش

- تغییر زبان باعث تغییر مجوز، مبلغ ذخیره‌شده، وضعیت رزرو یا رفتار API نشود.
- در localeهای RTL و LTR، ترتیب بصری، فرم‌ها، جدول‌ها، منوها و تمرکز صفحه‌کلید درست باشد.
- ترجمه مفقود هرگز کلید خام یا صفحه خالی نشان ندهد.
- قالب‌بندی پول و تاریخ بر اساس locale باشد و منطقه زمانی صریح باشد.
- تست‌ها روی fallback، جهت نوشتار، قالب‌بندی و عدم تغییر مقدار مالی اجرا شوند.
- گزارش نهایی فقط تست‌هایی را «موفق» بنامد که واقعاً اجرا شده‌اند؛ تا پیش از اجرای build/lint و تست‌ها، تغییرات ادغام نشوند.

## محدودیت‌های این بررسی

در این مرحله فایل‌ها به‌صورت ایستا از GitHub بررسی شده‌اند. اجرای واقعی `npm ci`، `npm run lint`، `npm run build`، تست مرورگر و بازبینی همه رشته‌های رابط انجام نشده است. بنابراین این سند نقشه شروع کار است، نه ادعای کامل‌بودن بومی‌سازی.
