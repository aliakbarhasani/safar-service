# ممیزی پذیرش Fleetbase در سفر سرویس

**تاریخ بررسی:** ۲۰۲۶-۱۰-۲۴  
**وضعیت:** ممیزی ایستا و تصمیم معماری اولیه؛ هنوز هیچ کد Fleetbase به سامانه عملیاتی سفر سرویس منتقل نشده است.

## تصمیم فعلی

Fleetbase فقط به‌عنوان یک موتور/سامانه مستقل لجستیک برای ارزیابی بیشتر در نظر گرفته شود؛ نه جایگزین هسته سفر سرویس و نه منبع مستقیم برای احراز هویت، کیف پول، قیمت‌گذاری یا چرخه مالی سفر.

تا زمانی که مجوز، وابستگی‌ها، هزینه عملیاتی و قراردادهای API بررسی نشده‌اند، ادغام کد آن یا افزودن سرویس Docker جدید به محیط اصلی مجاز نیست.

## شواهد بررسی فایل ZIP

- مخزن شامل API مبتنی بر Laravel/PHP و کنسول Ember.js است.
- قابلیت‌هایی که README پروژه معرفی می‌کند شامل Order Board، پیکربندی گردش کار سفارش، نقشه رهگیری سفارش، نقشه زنده ناوگان و محدوده‌های خدمت است.
- فایل `.gitmodules` نشان می‌دهد چند بخش مهم، از جمله `fleetops`، `core-api`، `iam-engine`، `ledger` و اجزای Ember در مخازن جداگانه نگهداری می‌شوند. بنابراین ZIP به‌تنهایی اثبات‌کننده یک نسخه کامل و قابل ساخت نیست.
- مجوز موجود در `LICENSE.md`، AGPL-3.0 است و README نیز مدل دوگانه مجوز را توضیح می‌دهد. قبل از کپی، فورک، تغییر یا عرضه شبکه‌ای، بررسی حقوقی مجوز و هر توافق تجاری لازم است.
- `docker-compose.yml` پورت MySQL را روی میزبان منتشر می‌کند و `MYSQL_ALLOW_EMPTY_PASSWORD: "yes"` دارد. این تنظیمات نباید بدون بازبینی و ایمن‌سازی وارد محیط واقعی شوند.
- در فایل‌های نمونه تنظیمات، مقدار توسعه‌ای `APP_DEBUG=true` دیده می‌شود؛ تنظیمات توسعه نباید به تولید منتقل شوند.
- تست‌ها و وابستگی‌های موجود در ZIP برای نتیجه‌گیری درباره ساخت موفق، امنیت یا آمادگی تولید کافی ارزیابی نشده‌اند؛ در این مرحله build یا تست اجرایی انجام نشده است.

## سازگاری با معماری سفر سرویس

- دروازه API موجود در `02-api-gateway` نقطه ورود کلاینت‌ها باقی می‌ماند؛ رابط وب یا موبایل نباید مستقیماً به Fleetbase متصل شود.
- قبل از انتخاب اتصال، باید مرز مالکیت داده بین سرویس‌های فعلی سفر/راننده/باربری و Fleetbase مشخص شود تا دو منبع حقیقت برای سفر، راننده یا وضعیت سفارش ساخته نشود.
- Fleetbase در صورت انتخاب، فقط مالک داده‌هایی باشد که صریحاً به آن واگذار می‌شوند؛ هویت، نقش‌ها، مجوزهای کاربران سفر سرویس و کیف پول/دفترکل مالی خارج از آن باقی بمانند.
- رویداد پایان سفارش/سفر نباید مستقیماً موجودی کیف پول را تغییر دهد. هر اتصال مالی آینده باید از قرارداد رویداد نسخه‌دار، اعتبارسنجی فرستنده، کلید idempotency، جلوگیری از پردازش تکراری، retry کنترل‌شده و امکان تطبیق/بازسازی استفاده کند.
- URLها، کلیدها، فعال/غیرفعال بودن یکپارچه‌سازی و تنظیمات کشور/زبان باید از تنظیمات امن محیطی و سامانه پیکربندی موجود خوانده شوند؛ اسرار نباید در مخزن ثبت شوند.
- برای زبان، ابتدا رابط موردنیاز سفر سرویس باید فارسی/دری و RTL را پشتیبانی کند. وجود پوشه ترجمه در Fleetbase به‌تنهایی به معنی پشتیبانی کامل RTL یا تجربه فارسی قابل قبول نیست.

## مراحل بعدی و معیار پذیرش

1. **تکمیل ممیزی نسخه و مجوز:** شناسایی commit/tag دقیق ZIP، فهرست وابستگی‌ها و وضعیت زیرماژول‌ها؛ تعیین کتبی مسیر مجاز استفاده از AGPL یا اخذ مجوز تجاری.
2. **تعریف مرز دامنه:** مقایسه APIها و مدل‌های Fleetbase با سرویس‌های موجود سفر، راننده و باربری؛ تعیین مالک هر داده و منبع حقیقت.
3. **نمونه آزمایشی جدا:** فقط پس از حل مجوز، اجرای Fleetbase در محیط ایزوله و غیرتولیدی با رمزهای قوی، عدم انتشار غیرضروری پورت پایگاه داده، DEBUG خاموش و داده آزمایشی.
4. **آزمون قرارداد API:** بررسی احراز هویت، مجوز، اعتبارسنجی ورودی، مدیریت خطا، timeout، rate limit، ثبت رخداد و قطع‌شدن سرویس خارجی.
5. **آزمون RTL و زبان:** بررسی واقعی فرم‌ها، نقشه، جدول‌ها، تاریخ/عدد و متن‌های راست‌به‌چپ؛ ترجمه ناقص نباید در رابط اصلی عرضه شود.
6. **تصمیم نهایی:** ادغام فقط در صورتی که سود عملی از نگهداری سرویس دوم بیشتر باشد و مجوز، امنیت، تست و روش بازگشت تأیید شده باشند. در غیر این صورت، قابلیت‌های مناسب به‌صورت الگو/قرارداد مستقل پیاده‌سازی شوند، نه با کپی کد ناسازگار.

## محدودیت‌های این ممیزی

این گزارش بر بررسی ایستای ZIP و اسناد قابل‌مشاهده تکیه دارد. در این مرحله، تست‌های Fleetbase اجرا نشده‌اند، امنیت آن ممیزی کامل نشده، سازگاری نسخه‌ها اثبات نشده و هیچ سرویس واقعی یا داده کاربری به آن متصل نشده است.
